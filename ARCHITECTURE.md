# EquationAI — Architectural Reasoning

*Why this project is built the way it is, and what I learned building it.*

## 1. Core thesis: why neuro-symbolic, not "just ask the LLM"

The obvious way to build a math-solving app is to send the problem straight to an LLM and display whatever it says. I didn't do that, because LLMs are fundamentally unreliable at arithmetic and symbolic manipulation — they predict plausible-sounding tokens, not verified calculations. A model can sound completely confident while being numerically wrong.

Instead, EquationAI splits the problem into two stages that play to different strengths:

- **The LLM (Gemini) only handles language.** It reads the natural-language problem and decomposes it into a structured, step-by-step JSON plan — defining variables, forming equations, deciding what operation each step represents.
- **SymPy handles all actual computation.** Every step's math is executed by a deterministic symbolic engine, not generated by the model.

This means the final numeric or symbolic answer a user sees was never "written" by the LLM — it was computed. The LLM's only job is figuring out *what* to compute, not *what the answer is*. That single design decision is what eliminates hallucination at the source, rather than trying to prompt the model into being more careful.

## 2. Sandboxing untrusted, LLM-generated code

Since the LLM's output is Python-like code that gets executed via `exec()`, that output has to be treated as **untrusted input** — not because the LLM is malicious, but because any system that runs generated code needs to assume it could go wrong, whether through a bug, an unexpected edge case, or a future prompt-injection style attack.

The executor restricts `__builtins__` to a curated allowlist — SymPy's own function names, plus a small set of genuinely harmless Python builtins (`min`, `max`, `sum`, `abs`, `len`, `round`, `sorted`, and basic type constructors) that legitimate math code needs constantly. Concretely, this means LLM-generated code can call `solve()`, `integrate()`, `min()` on a list of roots — but has no path to `__import__`, `open()`, `eval()`, or any other builtin that could touch the filesystem, run arbitrary commands, or introspect and re-enter the interpreter. This allowlist is scoped specifically to the actual threat (filesystem/process/import access), not to "everything not yet needed" — see Bug 3 below for what happens when that distinction gets blurred. **Known limitation:** restricting builtins alone doesn't fully close Python's object-introspection surface (reaching classes via `__class__`/`__subclasses__` attribute chains) — a genuinely adversarial input could still find a path around this. A production deployment handling untrusted public traffic should run this in a subprocess/container boundary or a real AST-allowlist evaluator, not rely on builtin restriction alone.

## 3. The mismatch verifier: catching hallucination directly

Splitting parsing from computation removes hallucination from the *final answer's arithmetic* — but it doesn't automatically catch every possible failure mode. To close that gap, the system prompt requires the LLM to independently state what it believes the final answer is (`expected_final_answer_sympy`), completely separate from the step-by-step execution.

After SymPy executes the full plan, a verifier compares the LLM's stated answer against the engine's actual computed result. If they disagree, the system flags it rather than silently trusting either side. This is a direct, deterministic hallucination check: it doesn't rely on the LLM being self-aware about its own uncertainty — it mechanically checks two independently-produced values against each other.

Building this out surfaced a real design subtlety: comparing symbolic answers isn't just string equality. Two mathematically identical expressions (`pi*log(2)/8` vs a rounded decimal `0.2722`) can look completely different as strings. The verifier tries numeric comparison first (with a small tolerance, to handle legitimate rounding from numerical fallbacks), and falls back to symbolic simplification (`sympy.simplify(a - b) == 0`) when the expression contains free variables that can't be reduced to a plain number — like general solutions to differential equations or line equations.

## 4. Why systematic evaluation, not spot-checking

Testing a handful of problems by hand tells you a system worked in the cases you happened to try — it doesn't tell you whether your system prompt actually generalizes across problem types, or where it quietly breaks. I built an automated, resumable evaluation harness specifically to answer that question honestly rather than assume it.

The suite covers arithmetic word problems, unit conversion, systems of equations, standard and hard integration (including non-obvious substitution tricks), differential equations, probability, combinatorics, coordinate geometry, series, linear algebra, 3D geometry, complex numbers, limits, optimization, statistics, and deliberately ambiguous, nonsensical, or adversarial inputs designed to test whether the system correctly recognizes when *not* to answer — or refuses to be hijacked.

This surfaced real gaps that spot-checking would have missed entirely — for example, the system prompt initially had no explicit guidance for differential equations, causing `dsolve()` to fail whenever the LLM defined the dependent variable as a plain symbol instead of an undefined function. That's exactly the kind of category-specific failure that only shows up with structured, categorized testing, not ad hoc examples.

The suite also distinguishes three outcomes, not two: auto-verified pass, genuine failure, and "solvable but has multiple mathematically equivalent valid forms" (needs manual review) — because a naive pass/fail scorer would incorrectly flag a correct-but-differently-formatted answer as wrong.

**Final result: 36/36 ground-truth accuracy** across an expanded 42-problem suite spanning 23 categories (6 additional cases correctly flagged for manual review due to multiple valid answer formats — not failures, see Bug 4 below for why that distinction matters), including **2/2 on adversarial prompt-injection resistance** — a test category not published by any comparable consumer math-solving tool I found (Photomath, Mathway, Wolfram Alpha, Symbolab).

## 5. Case study: four real bugs, and what they taught me

**Bug 1 — the undefined-symbol failure.** Partway through development, problems started intermittently failing with `name 'x' is not defined`. The root cause: when I updated the system prompt to add a new field, I accidentally removed the concrete example steps that had been implicitly teaching the LLM to always define symbols via explicit assignment (`x = symbols('x')`) before using them. Without that anchor, the LLM sometimes generated a bare expression (`symbols('x')`, no assignment) — valid Python, but it never actually stored `x` anywhere. The fix was restoring explicit examples and adding an explicit rule: *every symbol must be created via assignment, never assumed*. The lesson: system prompt examples aren't decoration — removing them silently degrades behavior in ways that only show up intermittently, which makes them easy to miss and important to test for deliberately.

**Bug 2 — the numeric-vs-symbolic verifier gap.** The verifier initially only handled numeric comparison (`complex(sympy.N(value))`). This worked for months of testing because every test happened to produce a plain number. It broke the moment I added differential equations and line-equation problems, whose correct answers legitimately contain free variables (`C1*exp(2*x) + C2*exp(3*x)`, `y = 2x - 1`) that can never be reduced to a number — `complex()` has no way to convert an expression containing an unbound variable. The fix was a two-path comparison: try numeric equality first, and fall back to symbolic simplification when the expression contains free symbols. The lesson: a verifier (or any test) that's only ever been exercised against one *shape* of answer will silently have blind spots for other valid shapes — expanding test coverage is what actually reveals those blind spots, not more testing of the same kind.

**Bug 3 — the sandbox blocked legitimate code, not just dangerous code.** Expanding the evaluation suite to new categories (3D geometry, optimization) surfaced a step that failed with `NameError: name 'min' is not defined` — the LLM had generated a perfectly reasonable `lower_bound = min(intersection_points)`. The cause: the sandbox restricted `__builtins__` to an empty dict, which correctly blocks dangerous builtins (`open`, `__import__`, `eval`) but also blocks ordinary, harmless ones (`min`, `max`, `sum`, `abs`, `len`, `round`, `sorted`) that legitimate math code needs constantly. Security and functionality were being conflated as if they were the same axis. The fix was a curated allowlist of specifically safe builtins, verified independently against both directions — confirmed `min`/`sum`/etc. now work, and confirmed `__import__`/`open`/`eval` are still blocked. The lesson: an allowlist should be scoped to the actual threat (filesystem/process/import access), not to "everything not explicitly needed yet" — the latter breaks correct code as readily as it blocks bad code, and the failures look identical (a `NameError`) until you actually check which one you're looking at.

**Bug 4 — the verifier's mismatch signal was being treated as ground truth, not a confidence signal.** While re-running the expanded evaluation suite, a 3D-geometry problem (finding a parallelepiped's volume via a determinant) kept getting scored as a failure — but the engine had actually computed the correct answer (1, confirmed against hand-calculated ground truth) on every run. What was actually failing was the LLM's own `expected_final_answer_sympy` self-check, which guessed wrong twice, with two *different* wrong answers (29, then 11) on two separate calls — a real, live demonstration of the exact unreliability this architecture exists to guard against. The real bug was two-layered: (a) the API route was treating any self-check disagreement as a hard failure and discarding the correct computed answer along with it, and (b) the evaluation harness itself was scoring `test_passed` as equal to the verifier's `is_valid` flag — meaning it was never actually comparing the engine's answer to the test's known ground truth at all, only checking whether the LLM agreed with itself. Fixing this required separating two genuinely different signals that had been silently collapsed into one: **ground-truth accuracy** (does the engine's answer match the known-correct value?) and **self-check agreement** (did the LLM's own independent guess match the engine?). The API now returns the correct computed answer with a `verification_warning` when only the self-check disagrees, instead of a 500 that throws away a right answer. The evaluation harness now scores accuracy by comparing directly against ground truth, with self-check agreement reported as a separate confidence metric. Corrected result: **36/36 ground-truth accuracy** (previously understated as 35/36 under the conflated scoring). The lesson: when a system has both a "did we get it right" measurement and a "how confident are we" measurement, silently using one as a stand-in for the other will eventually diverge — and when it does, it's easy to mistake a scoring bug for a correctness bug unless you go back to the actual ground truth and check.

A secondary bug, found via the same eigenvalue test, was more mundane but worth noting: the LLM used `Identity(n)` (a symbolic matrix expression) instead of `eye(n)` (SymPy's concrete identity matrix) when deriving a characteristic polynomial by hand, causing `.det()` to stay unevaluated and `solve()` to silently return `[]` — no error, just nothing. Fixed by adding an explicit system prompt rule preferring `.eigenvals()` directly (which sidesteps the whole class of mistake) with the corrected manual pattern as a documented fallback.

## 6. Tech stack

- **Frontend:** Next.js 16 (React 19), Tailwind CSS, KaTeX for LaTeX rendering
- **Backend:** FastAPI, Python
- **LLM:** Google Gemini (`gemini-2.5-flash`), via the current `google.genai` SDK (migrated proactively from the deprecated `google.generativeai` package)
- **Computation engine:** SymPy, sandboxed execution
- **Evaluation:** custom resumable test harness, 42 problems across 23 categories including prompt-injection resistance, JSON-logged results, ground-truth accuracy scored independently from LLM self-check agreement

## 7. What I'd improve next

- Add basic rate-limiting and lightweight auth before any public deployment with real user traffic — currently the only thing standing between this and abuse of my Gemini API quota
- Multi-part answers (e.g. "find both the width and the length") currently only surface through `final_answer_variable`, which holds a single value — the eval suite's `multi_part_word_problem` category exists specifically to track this gap until the schema supports multiple named final answers
- CI currently runs `pytest` on push but doesn't run the full evaluation suite automatically (the Gemini free-tier daily quota makes that impractical to run on every commit) — worth exploring a scheduled weekly eval run instead
- Self-consistency sampling (running plan generation 2-3 times and taking majority agreement) for higher-stakes problem categories, now that the ground-truth-vs-self-check distinction from Bug 4 makes it possible to actually measure whether this would help
